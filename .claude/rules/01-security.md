# 安全紅線

這份文件定義「不可逾越」的安全規則。即使為了趕進度或方便除錯，也不能違反以下任何一條。

## 1. 機密資訊絕不進版控

- `.env`、`.env.local`、`.env.*.local`、任何 API 金鑰、第三方服務 token、資料庫連線字串，**一律不可** `git add` / commit。
- 目前 `.gitignore` **尚未包含 `.env` 系列規則**，這是一個待修補的缺口。在第一次引入任何環境變數之前，務必先補上：

  ```gitignore
  # Env
  .env
  .env.local
  .env.*.local
  ```

- ✅ 正確做法：建立 `.env.example`（只放 key 名稱，不放真實值）進版控，讓其他開發者知道需要哪些環境變數；真實的 `.env` 留在本機或部署平台的 Secret 管理機制。

  ```env
  # .env.example（可進版控）
  VITE_API_BASE_URL=
  ```

  ```env
  # .env（不可進版控，僅本機）
  VITE_API_BASE_URL=https://api.example.com
  ```

- ❌ 錯誤做法：把帶有真實金鑰的 `.env` 直接 commit，或把金鑰硬編在 `src/` 任何 `.js`/`.vue` 檔案中。
- 若不小心已經 commit 過機密資訊，**金鑰本身視為已外洩**，必須立即在服務端輪換（rotate）該金鑰，單純 `git rm` 或改寫歷史並不足夠。

## 2. 前端環境變數的本質：不是秘密

- Vite 專案中所有以 `VITE_` 開頭的環境變數，**build 後會被打包進前端 bundle，任何人打開瀏覽器開發工具都能看到**。
- 因此：
  - ✅ 可以放：公開的 API base URL、第三方服務的「公開」可發布金鑰（如地圖服務的 public key）。
  - ❌ 不可放：資料庫密碼、後端 admin token、任何「擁有寫入/刪除權限」的密鑰。這類機密只能放在後端（Go/Rust 服務）的環境變數或 Secret 管理服務中，前端永遠不該知道它們的存在。

## 3. 前後端驗證責任界線（為未來接 API 預留）

本專案目前是純靜態資料、無後端，但這條規則要在**第一次接 API 之前**就建立共識，避免日後養成壞習慣：

- **前端驗證的本質是「使用者體驗」，不是「安全防線」**。例如表單必填檢查、Email 格式檢查、字數限制提示，這些只是讓使用者少跑一趟伺服器、即時看到回饋。
- **前端的任何驗證都可以被繞過**：使用者可以直接呼叫 API、用瀏覽器開發工具修改 request、用 Postman/curl 發送任意資料。因此：
  - ❌ 絕對不可以「因為前端已經驗證過格式，所以後端就不用再驗證」。
  - ✅ 後端（Go/Rust 服務）必須對所有輸入做**獨立、完整**的驗證：資料型別、長度、必填、業務邏輯規則（如：價格不可為負、權限是否足夠存取此資源）。
- **權限控管（authorization）一律由後端負責**，前端只能根據後端回傳的角色/權限資訊「決定要不要顯示某個按鈕」，不能把「能不能執行某操作」這個判斷邏輯放在前端。隱藏按鈕不等於擋住請求。

## 4. 第三方套件與依賴

- 新增 npm 套件前，留意其維護狀態（最近更新時間、issue 數量），避免引入長期無人維護或有已知資安漏洞的套件。
- 定期關注 `npm audit` 的輸出，但不要在沒理解風險的情況下盲目執行有破壞性的自動修復（如 `npm audit fix --force`）。
